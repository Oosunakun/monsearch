# コスト原文の表記調査

**Status:** 調査結果。解析方式・網羅的な文法の正式仕様ではない。

## 範囲と限界

Repositoryの`effect_cost_text / effect_costs`とコスト関連語を調査した。まとまった原文集合として確認できたのは[カードmock](../../app/utils/mockData/items/cards.json)で、482カード・605効果のうち非空コスト305件、空文字300件、非空原文はOrdinalで重複除去して90種類だった。

90種類すべての原文を確認したが、全カード種類・全時代のコスト表記を網羅する証拠はない。Database実レコードや網羅的な原文文法の存在は確認できていない。

## 解析方式を決める前に残る事例

| 原文 | 確認点 |
|---|---|
| `捨札1枚除外＆このユニットの□または弾消費` | ANDと選択の適用範囲を単なる区切り文字の出現では決められない |
| `手札1枚破棄(「錬金弾のカード」または戦闘スペルカード)` | カード条件中の「弾」は支払う弾枠ではない（D47確定） |
| `捨札9枚除外(…カードを3枚以上含むこと)` | 主数量9と条件数量3を区別する必要がある |
| `任意のスペル枠1～3つ消費` | 特定属性・multiとの対応と数量範囲の意味が未決定 |
| `▼～▼▼▼▼▼` | 記号による範囲指定 |
| `山札1体破棄` | 「枚」以外の単位。誤記と断定しない |
| `▼ 対象このユニット` | 対象情報がcost欄に混在 |
| `このユニット行動完了` | 現在のコストMappingに対応キーがない |

[裁定mock](../../app/utils/mockData/rules.ts)には引用中の`コスト：捨札１枚除外`もあり、全角数字を観測した。これは上記605効果の集計には含めていない。同資料の`□（完了型）特殊能力`のように、同じ記号が効果タイプを表す文脈もあるため、Repository全文章への記号一致ではコストを同定できない。

## Schemaの状態

[effect_costs](database/schema.sql)にはID・原文TEXT等があるが、種類・数量・選択肢・対象条件・解析状態の専用列はない。Effect全体の抽出情報を保持する`feature_effects`はあるものの、検索に必要なコスト構造が定義済みとは判断しない。

## Decisionと解析設計の分離

本仕様で追加確認する候補は、範囲・任意コストの一致条件、現在の語彙で表せないコストの扱い、判断できない原文を「コストなし」と誤判定しない規則。異なるコストParameterを同一Effect・同一選択肢内でANDにする規則はD44で合意済みであり、再検討しない。

解析方式（正規表現・文法・辞書・手動整備等）、内部表現、解析状態の保存、既存90種類を用いた検証方法は別途設計する。観測した原文だけから網羅的なルールを推測して正式採用しない。Schema変更の必要性も、この設計結果に基づいて判断する。

## 調査後の合意（D49〜D52）

- 数量範囲はいずれかの許容数量が指定個数以上なら一致する。
- 任意のスペル枠は、指定種類の枠を支払いに使えるかで判定する。属性の文字出現だけでは決めない。
- ANDでは指定した各Pairを同時に満たす支払い方を要求し、同じ枠を複数Pairに重複計上しない（D53）。任意1〜3枠に対する火2＋水1は一致、火2＋水2は非ヒット。
- 行動完了等、個別検索キーがないコストもDomain上は存在する。その他コストなし・全種類コストなしに一致させない。
- Domain Semanticsと構造化・解析設計を分け、構造化と検証が完了するまでコスト検索は公開対象としない。解析不能時の部分検索や非ヒットfallbackは正式採用しない。

## 現実装と公開前提の差

### 代替払いの追加調査（D64）

cards.jsonのコスト・効果本文、rules.ts、docs、型定義を調査したが、明示された任意枠以外の一般的な代替支払い規則を確定する資料は見つからなかった。`このユニットの■または＊消費`、`このユニットの□または＊消費`は個別効果の選択肢であり、`このユニットの魔＊消費`は記号の併記で、一般代替規則の説明ではない。ユーザー指示に従い仮想的なルールを追加せず、D50・D53と明示された選択肢の範囲を維持する。

### 公開制御

[SearchFormEffect.vue](../../app/components/cards/search/layout/SearchFormEffect.vue)は3種類のコスト入力を表示し、BuilderはURLへ出力、[cards.get.ts](../../server/api/cards.get.ts)の共通Parserはコスト条件を復元する。一方、[search.ts](../../server/utils/cardSearch/search.ts)にはコスト条件の評価がない。コスト用の公開制御は調査対象では見つからない。

そのためD52は、現在の露出と受理に対する制御の改訂も必要とする。UIを非表示にするだけでは既存URL・直接APIを制御できない。未提供時の応答・表示・公開完了基準は別設計とし、条件を適用していない結果を適用済みとして扱わない。

002はURL変換、009は既存JSONによる検索のバックエンド移行が範囲であり、コスト構造化やmigrationを定義していない。新たな公開前提を本仕様に記録し、その実現を別設計とする整理は責務と整合する。009の旧検索集合維持を新しい公開前提の実現にそのまま適用しない。
