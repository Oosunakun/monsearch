# カード検索サイトの情報設計方針（整理版）

## 前提

このサイトは「カード検索サイト」であり、主目的は：

* カード検索
* カード詳細確認
* 関連ルール確認

です。

ただし、現状のゲーム環境では：

* 公式ルール情報が散在している
* 過去情報の保守状態が曖昧
* プレイヤー間で運用解釈が分岐している

という背景があり、

> 「カード検索を起点として、散在したルール情報へ到達できること」

にも価値があります。

そのため、このサイトは：

# 「ルール制定サイト」ではなく

# 「情報整理・索引サイト」

として設計します。

---

# サイトの基本スタンス

このサイトは以下を重視します。

* 事実ベースで情報を整理する
* 独自解釈をできる限り避ける
* ユーザーに解釈を委ねる
* 公式情報を引用ベースで整理する
* 非公式ファンサイトとして過度な権威性を持たない

特に重要なのは：

# 「このサイトがルール体系を定義しているように見せない」

ことです。

---

# 採用しない方針

以下は意図的に避けます。

## 「レギュレーション」中心設計

理由：

* 適用期間・範囲が曖昧
* 過去環境が未保守
* プレイヤー解釈が分裂している
* サイトが環境定義者のように見える

ため。

---

## 「公式ルール」など権威性の強い名称

理由：

* このサイトは非公式ファンサイト
* 公式情報の整理は行うが、公式主体ではない
* 「公式」を強く出すと誤認を招く

ため。

---

## ルール情報の完全統合ページ

理由：

* モバイルで情報密度が破綻する
* 使用制限とQ&Aは意味が異なる
* 一覧性が失われる
* DB構造変更コストが大きい

ため。

---

# 採用する基本構造

## メニュー構成

```txt
カードリスト
詳細検索
使用制限
ルール
大会情報
About
```

この構造は：

* 中立的
* 事実ベース
* 非権威的
* 立場を主張しない

ため維持します。

---

# 使用制限ページ

```txt
制限リスト
├─ 注意事項
├─ 使用できるカードセット
├─ 禁止カード、制限カード
├─ 召喚術師と紐づくカード
└─ アーカイブ（アコーディオン）
   └─ 過去の使用制限
```

## 目的

* 構築制約確認
* 現在の使用可否確認
* 制限カード確認

---

## 「カード別一覧」の役割

ここで重要なのは：

# 「通常と異なるカードのみを掲載する」

ことです。

つまり：

* 禁止
* 制限
* 特殊条件

など、「注意が必要なカード」のみを一覧化します。

全カードを載せる一覧ではありません。

---

# ルールページ

```txt
ルール
├─ 注意事項
├─ カード裁定
│  ├─ テキスト変更
│  └─ エラッタ
├── Q&A
├── 補足
└─ アーカイブ（アコーディオン）
   └─ 過去のカード裁定
```

---

# 「カード裁定」を採用する理由

「エラッタ」だけでは：

* テキスト誤記修正

の意味が強すぎます。

しかし実際には：

* 読み替え
* 旧カード互換運用
* ルール変更追従
* 解釈補完

も含まれます。

そのため、

# 「カード裁定」

という比較的中立的な分類を採用します。

---

# Q&Aを独立させる理由

Q&Aは：

* ルール解釈
* 挙動確認

が目的であり、

読み替え・エラッタのような：

* テキスト変更系

とは性質が異なります。

混在すると一覧性・俯瞰性が悪化するため、独立管理します。

---

# 重要な設計判断

## 詳細全文は横断表示しない

理由：

* 各ページで情報網羅範囲が異なる
* 「ここに全情報がある」と誤認される
* 更新同期ズレが発生する
* 一覧性が崩れる

ため。

---

# 採用するのは：

# 「主情報＋関連ラベル」

方式です。

「関連：[エラッタ]」というラベルをクリックした際、単にルールページのトップに飛ぶのではなく、そのカードの箇所まで自動スクロール（アンカーリンク）するように設計する

# DB設計方針

## 完全統合DBは行わない

理由：

* 既存スキーマ破壊コストが高い
* 更新責務が異なる
* 情報寿命が異なる

ため。

---

# 採用予定

## 横断VIEW / summaryテーブル

イメージ：

```txt
card_id
has_restriction
has_errata
has_qa
qa_count
last_updated
```

程度。

つまり：

# 「全文統合」ではなく

# 「索引・存在通知」

を行う。


# 「カード詳細ページ」への集約（Could have）
各リスト（使用制限／ルール）はあくまで「入り口」とし、最終的な「カード詳細ページ」に全ての情報（現在の制限状況、最新のエラッタ、関連Q&A）がカード単位で集約されていると、デック作成時のナビとしての価値が上がる。

# 「更新日」の重要性
各ページの最上部か、ラベルの横などに「公式反映日：202X/XX/XX」といった表記があると、ユーザーが判断しやすくなります。


---

# archive方針

archiveは：

* 現行構造と同じ構造
* 時代別に分離
* 初期表示は現行のみ

とする。

理由：

* ユーザー学習コストを下げる
* 過去情報との混線を避ける
* 現行運用を優先する

ため。

---

# モバイル方針

ルール情報は情報量が多いため：

* 一覧はv-card型
* 詳細はモーダルまたは別ページ
* PCのみ詳細テーブル表示可

とする。

---

# 最終的なサイトの本質

このサイトは：

# 「カード検索を中心としたルール索引サイト」

であり、

# 「ルール制定サイト」ではない。

そのため、

* 断定を避ける
* 出典を明記する
* 情報存在を整理する
* 解釈はユーザーに委ねる

という立場を維持する。
